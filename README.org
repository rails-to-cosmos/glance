* Glance — Repository Overview

** Summary

*Glance* is an experimental /stateful org-mode parser/ written in *Haskell*. Its goal is to explore org-mode parsing combined with database interactions, providing a system for managing, querying, and relating org-mode content.

- *Author:* Dmitry Akatov

** Quickstart — headlines in a browser tab

#+begin_src sh
cabal run glance -- serve --dir ~/org
#+end_src

Then open =http://127.0.0.1:7777/=. The page fetches =/headlines= and mounts
=table-view.js= on it: one row per headline, with the state badge, priority,
title, tags and the scheduled/deadline dates. Click a column header to sort,
press =/= to summon the filter palette and narrow.

- =--port N= — default =7777=.
- =--assets PATH= — the directory holding =table-view.js=, default the sibling
  =table-view/web= checkout. When it is missing, =/= says so and =/headlines=
  keeps working; the JSON stands on its own:

#+begin_src sh
curl -s localhost:7777/headlines | jq '.rows | length'
#+end_src

The response body is the table-view View object and nothing else — the load
counts ride in =X-Glance-*= headers (rows, files, parse, decode and read
failures).

*Filter and page it, and pay for bytes only when something moved.* =/headlines=
takes four parameters and answers with the same View object:

#+begin_src sh
curl -s 'localhost:7777/headlines?q=meeting' | jq '.rows | length'
curl -sD - -o /dev/null 'localhost:7777/headlines?limit=1000&offset=2000'
#+end_src

- =q= — a case-insensitive substring of the row /as it displays/: a bracket link
  matches by its description, and a query never spans two cells. The store keeps
  that text per row, so filtering 13k rows costs one substring scan rather than
  3 MB of JSON on the wire.
- =limit= — page size, at most 20000. Absent means the whole set, which is what
  a client that wants to sort and move locally should ask for.
- =offset= — where the page starts, default 0.
- =order= — =scheduled= (the default) or =document=; see /Outline depth/ below.
  Anything else is a 400, since a misspelling that quietly served the sorted
  view would look exactly like a working request.

The filter runs before the page, so =X-Glance-Total= is the match count and
=X-Glance-Has-Next= says whether another page follows. A page is cut out of the
view's own declared sort (scheduled ascending), so page two is the rows the
table would show after page one; sorting a /page/ in the browser reorders that
page alone, while the no-limit mode keeps full-fidelity client-side sort.

*Outline depth, and reading the tree back (experimental).* Every row carries a
=depth=: 0 for a top-level headline, one more per star past the first.
[[file:../table-view/SCHEMA.md][SCHEMA.md]] marks it a renderer hint, so it is a
field of the row rather than a cell, a column or a filter key, and a renderer
that draws no tree ignores it.

Depths only read as a tree while the rows are in the order they nest, and the
default view sorts them apart by =SCHEDULED=. =?order=document= is the pairing
that makes them legible: the rows stay in walk order whatever the limit — file
by file, headline by headline down each — and the view carries *no =sort= field
at all*, so a renderer leaves them where they landed.

#+begin_src sh
curl -s 'localhost:7777/headlines?order=document' | jq '.rows[:4] | map({id, depth})'
curl -s 'localhost:7777/headlines?order=document' | jq 'has("sort")'   # false
#+end_src

There is no UI for it: the shell never asks, so this is a URL you type. The
browser renderer draws depths under its own =tree: true= mount option — muted
=│ ├─ └─= guides in the title column, degrading to plain indentation under any
sort or filter, since a connector claims a parent that a reordering makes up.
Wiring the shell's mount to it is the step this stops short of, deliberately:
the option is experimental on both sides and neither carries invariant weight
yet.

Every answer carries =ETag: "<fingerprint>-gN"= — the fingerprint being a
digest of the tree the daemon loaded, =N= the store's generation, which the file
watch moves whenever a response would change — under =Cache-Control:
no-cache=, so a browser revalidates every time and an unchanged tree costs a
0.6 ms 304 instead of a 3 MB body. One tag serves every variant: the parameters
are in the URL and an HTTP cache is keyed by URL, so =?q=foo= and =?q=bar= are
separate entries revalidating against their own tags. Responses are gzipped
(3.06 MB → 580 KB for the whole set, 34 KB → 15 KB for the renderer) with the
=Vary: Accept-Encoding= that goes with it.

*Filtering is a query language.* The filter is summoned rather than resident:
=/= raises a palette over the table, the way a minibuffer opens, and an
unfiltered table carries no filter chrome at all. It speaks
[[file:../table-view/SCHEMA.md][SCHEMA.md]]'s micro-syntax and the server parses
it: =state:TODO state:DONE tanik= is either state and the text, because
distinct keys and free text AND. A =key:value=
is a predicate only when =key= names a column — =state=, =priority=, =title=,
=tag=, =scheduled=, =deadline= — or one of your own org tags, so =:work:= and
==code== stay the org text they are. Tags are keys of their own:
=contact:tanik= is "tagged =contact= and matching =tanik=", and =contact:= alone
is the facet. Two predicates on one key combine by what the field holds: one
value means either of them (=state:TODO state:DONE=, since no row is both),
a list means all of them (=tag:web tag:glance= carries both, the way a label
filter reads). =-token= negates, ="two words"= quotes, =key:none= asks for an
empty cell, =scheduled:2026-08= is the month, and =state:*active*= /
=state:*inactive*= are the keyword groups your =#+TODO:= lines declare (=active=
and =inactive= without the stars mean the same thing). A query
with no predicate in it is the substring search it always was. The applied query
rides in the URL, so a filtered view is a link; =DEL= over the table takes the
last token back off.

*The default view is your active work.* Open the page with nothing in the
address bar and it applies =state:*active*= for you — every keyword your
=#+TODO:= lines declare before the bar, which is the work still to do. It is a
query like any you typed: it shows as a chip, it is in the URL, and =DEL= over
the table strips it, at which point the whole tree is on screen. Ask for
something else — =?q=tag:travel=, or an empty =?q== for everything — and that is
what you get; the default is only ever injected when the URL says nothing.

*The page stays tiny.* The shell is inline vanilla JavaScript — no framework, no
build step, no dependency, nothing fetched off this server. It boots on
=?limit=100= — a window's worth, painted well ahead of the whole set's ~250 ms —
pulls the rest in behind the painted table so movement and sorting see
everything, hands the filter to the server rather than narrowing locally,
and opens its socket with =?bootstrap=off= because it already has the rows.

*The tab stays live.* The directory is walked and parsed once, at startup, into
an in-memory store; a request then costs an encode rather than a walk (0.09 s
for 13344 rows against 14.5 s per request before). A file watcher re-parses one
=.org= file per edit — 4 ms — and pushes the difference over =ws://.../ws= as
table-view's streaming ops: =set-rows= once on connect (=?bootstrap=off= drops
it for a client that fetched the rows over HTTP), then =upsert-row= and
=delete-row= per change. Edit a headline in Emacs and the open tab moves in
about 100 ms, no reload; create or delete a file and its rows appear or go. A
green dot in the top-right corner says the socket is up, grey that it is
reconnecting.

*Materialize a headline.* The view declares one action — =RET → materialize= —
so hitting =RET= on the selected row (or double-clicking it) opens that
headline over the table as *two panes*: a textarea holding the subtree's text —
stars, planning line, body and every child, exactly as the file spells them —
and a *properties panel* beside it holding the headline's own drawer, a row per
property in the order the file writes them. =ORG_GLANCE_ID= is shown like any
other row, with a line under it saying what it is — the row id *is* that value,
so renaming it renames the row.

*The panel is modal*, dired's shape rather than a form's. In *nav* the rows are
read-only text with a cursor on one of them and nothing focusable at all, which
is what leaves the plain letters free: =n= / =p= and =j= / =k= both move the
cursor, under either profile, and so do the arrows. =RET= opens the row at
point, and only then are there fields to type into: the value takes the focus,
except on the trailing empty row, where the key does. Inside an open row =TAB=
hops between its two fields, =RET= commits it and goes back to nav, and =ESC=
puts back the text the row was opened on. The last row is always empty: commit
something into it and the next empty one appears under it, cursor and all, which
is the whole of the "add" affordance, since there is nothing to press. Empty a
key and that property is deleted on the next sync.

=TAB= crosses between the panes — out of the text into the panel's cursor, out
of nav back into the text — and the cursor is where you left it. There are two
stops, so =S-TAB= is that same toggle rather than a second walk. The crossing is
suspended while a row is open, since inside one row =TAB= has the two fields to
mean. The raw shape =C-c '= swaps to has one pane and nothing to cross to, so
=TAB= is the browser's again there.

The sheet has no buttons. =ESC= is a ladder: over an open property row it is
that row's and puts it back, so the sheet only ever sees the key from nav.
=ESC= from there, or a click outside the box, closes it —
flushing first when *either* pane has moved, and closing on the server's 200; a
sheet you only read closes with no request at all and touches no file. The write
goes back over the same character span, leaving every other byte alone, and the
row arrives a moment later over the socket, because the file watch is what
updates the table whoever did the writing. =C-x C-s= syncs mid-edit and chains
the receipt's digest, so a long session of edits costs no re-materialize. If the
file moved in between — Emacs saved it, a sync landed — the flush is refused and
the sheet stays open saying =conflict=: =C-x C-s= then re-reads the file's digest
and writes your text over it, and =ESC= discards. Closing the tab on an edited
sheet flushes on the way out. The header says which of =synced= / =syncing…= /
=conflict= / =error= it is in — the last two name the key that clears them — and
the sheet wears Hack over the page's own danneskjold.

=C-c '= — org's own =org-edit-special= — swaps the sheet between the two panes
and the raw subtree with the drawer spelled out in the text. It works by asking
the server for the headline again rather than by rearranging anything in the
browser, so an edited sheet is refused with =sync first — C-x C-s=. That is
deliberate: the split between body and drawer is the *server's*, and there is no
org parser in the page to do it locally.

A property nobody edited is written back as the very line it came in on —
spacing, indentation and all. Only a value you changed is re-rendered, as
=:KEY: value= under whatever indentation the drawer already uses. Decompose and
recompose an untouched headline and the file is byte-identical. The same round
trip from a shell, =id= being the row id the view carries:

#+begin_src sh
curl -s -G --data-urlencode 'id=ROW-ID' localhost:7777/headline
# → {"org": …, "body": …, "properties": [["ORG_GLANCE_ID", "…"], …], "digest": …, "span": …}

# The whole subtree, as before:
curl -s -X POST -H 'content-type: application/json' \
     -G --data-urlencode 'id=ROW-ID' localhost:7777/headline \
     --data-binary '{"org": "* DONE …\n", "digest": "<the digest the GET returned>"}'

# Or the two panes apart, which is what the sheet sends:
curl -s -X POST -H 'content-type: application/json' \
     -G --data-urlencode 'id=ROW-ID' localhost:7777/headline \
     --data-binary '{"body": "* DONE …\n", "properties": [["EFFORT", "0:45"]],
                     "digest": "<the digest the GET returned>"}'
#+end_src

Both shapes take the same optimistic lock and the same 409s; naming both in one
body is a 400, and an empty =properties= list removes the drawer.

*Settings: the keyword cycles, from the page.* =C-c C-,= opens a second sheet
over the table, one section per keyword layer: =system.org= for the whole tree,
then a section per =tags/TAG.org=, then a read-only preview of the union they
add up to. Each editable section is one box holding that file's =#+TODO:= lines
*verbatim* — the config files are org and that line is the contract, so what you
edit is the line rather than a chip UI over a guess at what it means. A tree
that has never had a =system.org= still lists it, marked =not created yet=: type
a cycle into it and the file, and the directories over it, are created on the
way out.

It is the materialize sheet's own pattern, down to the words. No buttons: =ESC=
or a click outside syncs the sections that moved and closes, a sheet you only
read closes with no request, =C-x C-s= syncs mid-edit, and the header carries
=synced= / =syncing…= / =conflict= / =error=. Each section is its own file, its
own write and its own lock, so one that Emacs moved underneath you refuses on its
own line while the rest land. What comes back is the *whole tree reparsed*: a
keyword that has just started existing is recognized in files nobody touched, so
the daemon reseeds, the badge palette moves, and every open tab re-fetches. On a
touch device, where there is no chord to type, a gear appears in the status
corner — the same exception the filter's chip row is.

#+begin_src sh
curl -s localhost:7777/config
# → {"layers": [{"path": …, "tag": null, "lines": ["#+TODO: TODO | DONE"], "digest": …},
#               {"path": …, "tag": "book", "lines": […], "digest": …}],
#    "keywords": {"active": […], "inactive": […]}}

curl -s -X POST -H 'content-type: application/json' localhost:7777/config \
     -d '{"path": "…/.org-glance/config/system.org",
          "lines": ["#+TODO: TODO STARTED | DONE CANCELLED"],
          "digest": "<the digest the GET returned>"}'
#+end_src

The write is the same span splice every other write is: only the =#+TODO:=
lines are replaced, so a =#+TITLE:=, a comment and the capture template
org-glance keeps in those files come back byte for byte. A file with no such
line takes one under the header it opens with. Posting an empty =lines= deletes
the layer's cycle. An empty =digest= is the pin for a file that is not there
yet — and a file that turned up meanwhile refuses exactly as a moved one does,
rather than being overwritten. Lines that are not =#+TODO:= pragmas, and pragmas
that declare no keyword org would read, are 400s with nothing written.

The store stays a projection and the org files stay the source of truth: it is
thrown away with the process, every row in it came out of a file, and a file
that stops parsing keeps the rows it had — including one saved from the browser
with a typo in it, which is the same deal any editor offers. Restart the daemon
and the tab re-fetches and re-mounts on its own, backing off from 1 s to 30 s.

*Two keys write without opening anything.* =D= archives and =C-c C-t= sets a
state, and both run over the *marked set* when there is one and over the row at
point when there is not — dired's rule, and org-glance's. Mark a run of rows
with =m=, press =D=, and the pill says =D → archived (5)=. There is no
confirmation: the page sends row ids and a name, the server works out which
characters to move, and the rows come back over the socket a moment later
because the file watch is still the only thing that updates the table. What
makes that safe is the same optimistic lock the sheet uses — a file that moved
under you refuses its rows and says so in the log, while the rest land.

=C-c C-t= raises a small palette of the states your files declare, plus =clear=
to take a keyword off. Type to narrow it, =C-n= / =C-p= or the arrows to walk
it, =RET= to commit, =ESC= to leave. A keyword is legal per *file*: the palette
offers the union of every =#+TODO:= line loaded, and a command naming one that a
row's own file does not declare is refused whole rather than applied to the rows
whose files do. The same two commands from a shell:

#+begin_src sh
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "set-state", "ids": ["ROW-ID", "OTHER-ID"], "args": {"keyword": "DONE"}}'
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "archive", "id": "ROW-ID"}'
#+end_src

Rows are grouped by the file they live in and each file is written *once*, so a
marked set spanning three files is three atomic writes rather than one per row.
The answer is per id — =[{"id": …, "ok": true, "digest": …}]=, or an =error=
where a file had moved — in the order you named them.

*=D= archives; it never deletes.* The tag org uses goes on the headline
(=:web:glance:= becomes =:web:glance:ARCHIVE:=, and a headline with no tags gets
=:ARCHIVE:= appended to its title line) and everything else about the file stays
where it was. Pressing =D= twice costs nothing: a row already carrying the tag
is left alone. What makes an archive worth having is the other half — the table
leaves archived rows out unless you ask for them:

| query              | what you get                                 |
|--------------------+----------------------------------------------|
| (nothing)          | everything except archived rows              |
| =archive:=         | the archived rows                            |
| =-archive:=        | everything except them — the default, spelled |
| =archive:tanik=    | archived rows matching =tanik=                |

Any query that mentions the =archive= key at all turns the default off, and the
response's =X-Glance-Archived= header says how many rows were left out, so an
empty table can be told from one whose matches are all filed away. The key stays
in the vocabulary whether or not the default is hiding its rows, which is what
makes it reachable at all: the filter is parsed against every tag in the tree,
and only the rows are narrowed.

*Keys.* The page carries org-glance's =overview-mode= map, under org-glance's
own command names, and echoes what it did in a pill in the bottom corner — the
pending prefix while one is open (=C-c -=), the command and its help line on
completion (=C-c C-t → org-glance-overview:todo=), =C-c z is undefined=
otherwise, and the prefix drops after two seconds. Movement drives the renderer's own row selection, and comes
in an =emacs= profile and a =vim= one.

Both key profiles share everything that is not movement:

*One of those does not survive the browser.* =C-c C-t= is bound, dispatched and
claimed by the page — and in Chromium the second chord never arrives, because
=Ctrl+T= opens a tab in the browser process above the document and
=preventDefault()= cannot reach it. Firefox reserves it the same way. The page's
half is correct and tested; there is nothing a page can do about the other half.
Until the binding is moved, set a state from the shell (=POST /command= above)
or from Emacs.

*Movement* is the part that differs. =emacs= is org-glance's overview map, and
the default:

| key   | =emacs=                                   | =vim=                   |
|-------+-------------------------------------------+-------------------------|
| down  | =n=                                       | =j=                     |
| up    | =p=                                       | =k=                     |
| right | =f= → =next-column=                       | =l= → same              |
| left  | =b= → =previous-column=                   | =h= → same              |
| top   | =,= =<=                                   | =,= =<= =gg=            |
| end   | =.= =>=                                   | =.= =>= =G=             |
|       | =g= → =org-glance-overview:refresh=       | =R= → same              |
|       | =j= → =org-glance-overview:open= (staged) | =!= carries it (shared) |

Two rows move to make room under =vim=, and both moves are why the profiles are
data rather than a second dispatch: =j= is down there, so the open-stub is left
to =!= — which =org-glance-overview-mode-map= already carries, as its
dired-execute rhyme — and =g= is a prefix rather than a command, so refresh goes
to =R= and reads as vi's reload. Nothing binds a bare =g= under =vim=: a
complete sequence that also opens a longer one would leave =gg= unreachable.

Horizontal movement selects a *cell*. =f= and =b= are org-glance's same-level
keys one granularity down — where the overview walks headlines with them, a
table walks the cells of a row — and =vim= spells the same two commands =l= and
=h=. A row selection starts with no column and looks exactly as it always did;
the first horizontal key lands on the first column whichever direction asked
for it, and from there =n=/=p= (=j=/=k=) carry that column down the table.
Walking off either edge stays on it. The echo names where it landed by the
column's own header — =f → next-column (Headline)=, or =f → next-column (at
last)= at the edge. The column lives in the renderer's selection rather than in
the page, so switching profiles mid-table keeps it and clearing the selection
takes it with it.

Rows *mark* the way dired's do. =m= toggles the mark on the row under the cursor
and steps to the next, so a held =m= walks a column laying marks down; =u= only
ever takes one off, and steps too, so a held =u= clears a column rather than
flickering it; =U= drops the lot. Each echoes the count the renderer keeps
(=m → marked (3)=, =U → all marks cleared=), and the renderer's own status line
leads with =3 marked ·= while any stand. The marks themselves are the
renderer's, keyed by row id: a marked row that a filter hides, that a page turn
leaves behind or that a sort moves is still marked, and still counted, because
the count is what a bulk action would run over. Nothing on this page keeps a
second copy of them.

The set is shown a *page* at a time — 100 rows, the same count the first paint
asks the server for, so the opening screen is exactly page one and everything
arriving behind it only adds pages to turn to. The pager reads in the renderer's
own status line (=1–100 of 12,870 · ‹ prev · next ›=) and is absent while there
is one page. =]= and =[= turn one and echo where they landed — =] → page 3/129=.
Row movement crosses the boundary by itself: =n= off the last row of a page
lands on the first row of the next, =p= off the first lands on the previous
page's last, and the column rides along either way. Where the page ends is the
renderer's to know, since only it knows there is one. The buffer-ends keys reach
the ends of the page on show — =,= and =.=, and =gg= and =G= under =vim= — so
=[= and =]= are how you leave it.

Switch in the status corner, top right: the connection dot, a =theme:= selector
and a =keys:= selector sit there in that order. The keymap one rebinds in place,
echoes =movement: vim=, and remembers the choice in =localStorage= under
=glance-keys=; =?keys=vim= in the URL picks a profile and remembers it too. Both
are native =select= elements, so Tab reaches them and the arrows walk them
without a chord of their own.

*Light or dark, and no flash either way.* =theme:= offers =auto=, =light= and
=dark=. =auto= follows the system's =prefers-color-scheme= and is the default;
the other two stamp =data-theme= on the document element and pin it, and
choosing =auto= again takes the attribute back off. The choice is remembered in
=localStorage= under =glance-theme=, and a one-line script in the =<head>= reads
it and stamps the attribute before the first paint, so a dark-themed page never
flashes light on the way in. The whole page wears danneskjold through one set of
=--g-*= variables — surface, text, muted text, border, selection — and the
materialize sheet keeps a single =--dk-mono= of its own, the Hack font stack.

The page's last line is that map, resident: =n/p rows · f/b cells · [/] pages ·
RET materialize · / filter · g refresh · DEL drop token · q quit= under =emacs=, and
=j/k=, =l/h= and =R= in their places under =vim=. It is named by command and
spelled from the same blob the dispatch reads, so switching profiles rewrites it
and it can never offer a key nothing is bound to. The pill says what just ran;
the line says what can.

The page itself never scrolls. It is one column the height of the window — the
table, the log under it taking whatever is left, the key line last — and the two
boxes that can outgrow their room scroll inside themselves, so the corner and
the key line hold their places whatever arrives.

A staged key is recognized in full and then says what it is waiting for: the map
is complete ahead of the commands that will back it, which reads better than a
key that silently does nothing. The keys are inert while a text field has focus
— typing in the palette or the sheet types — and while the property panel is
holding them, which it does with nothing focused at all; the exceptions are
=C-x C-s=, =C-c '= and =ESC=, which is what makes the sheet's Emacs muscle
memory work, over the properties panel as much as in its textarea. =C-c= and =C-x= become
prefixes only with the selection collapsed, so a copy or a cut is still one, and
=C-l=, =C-r=, =C-t=, =C-w=, =C-n=, =C-p= and =<f5>= always reach the browser —
which is why neither profile moves on =C-n= or =C-p=, however much Emacs would
like to.

*On a touch device there are no keys*, which is the one exception the
keyboard-first rule makes. A coarse pointer gets the chip row as a tap target —
44px of it, reading =filter …= while nothing is applied — and tapping it summons
the palette =/= summons. The sheet's textarea and its property fields are 16px
there, since iOS zooms the page in on anything smaller and does not zoom back
out, and the two panes stack rather than sitting side by side. A mouse or a
trackpad sees none of this: every rule is inside =@media (pointer:coarse)= and
the tap handler asks the same query before it runs. A narrow window stacks them
too, by wrapping rather than by a breakpoint of its own.

The whole page is monospace — /JetBrains Mono/, /Fira Code/, /SF Mono/, Menlo,
Consolas, whichever is installed. Nothing is fetched for it. Drop a
=JetBrainsMono-Regular.woff2= (or =.ttf=) into the =--assets= directory and the
shell declares an =@font-face= against it and serves it from there; leave it out
and the stack falls through, silently.

*What is not walked.* org-glance keeps its canonical store under
=.org-glance/data/= and writes overview and agenda buffers beside it under
=.org-glance/overviews/= and =.org-glance/meta/=, repeating the same headlines
under the same =ORG_GLANCE_ID=. Those two directories are skipped — org files
are the source of truth, and a derived render of one is not a second headline.
Over =~/sync= that is 514 fewer rows and one duplicated row gone from a filtered
table. =--include-derived= walks them anyway, on =serve=, =desktop= and =scan=.
Where two files still claim one id, the =.org-glance/data/= copy wins and the
rest are counted in =X-Glance-Id-Collisions= and listed by =glance scan=.

The listener binds =127.0.0.1= and nothing else. Authentication and the
read/write/automate tiers arrive with the protocol step (S7 in
=docs/plan-org-console-web.md=); until then the loopback interface is the whole
access-control story.

** Desktop — the same server, in a window of its own

#+begin_src sh
cabal run glance -- desktop --dir ~/org
#+end_src

The same daemon =serve= runs, with an app-mode browser window opened on it the
moment the socket is listening: no address bar, no tabs, no chrome. It takes
=serve='s flags — =--dir=, =--port= (default 7777), =--assets=,
=--include-derived= — plus two of its own:

- =--browser CMD= — what to open the window with.
- =--dry-run= — print the command that would be run and the URL it would open,
  then exit. Nothing is bound and nothing is started, so it is the way to see
  what this machine resolves to:

#+begin_src sh
cabal run -v0 glance -- desktop --dir ~/org --port 7797 --dry-run
# glance desktop — http://127.0.0.1:7797/
#   window:  /usr/bin/chromium --app=http://127.0.0.1:7797/
#   dry run — nothing started.
#+end_src

*Which browser.* =$GLANCE_BROWSER= first, then =--browser=, then the first of
=chromium=, =chromium-browser=, =google-chrome-stable=, =google-chrome=,
=brave=, =vivaldi= found on =PATH= — each run as =CMD --app=http://127.0.0.1:PORT/=.
The environment leads so a machine whose browser is on none of those lists can
be set up once, in a shell profile, and be obeyed by every launcher too. What it
names has to be a chromium-family browser: =--app= is the flag that drops the
chrome, and Firefox no longer has it.

With none of them installed, =xdg-open= opens the URL as a plain tab instead —
a worse window and a working one. With no =xdg-open= either, the URL is printed
and the server keeps serving: a missing browser never takes the daemon with it.

*Closing the window leaves the daemon running.* It is a browser window, and the
server behind it is a server — closing it is closing a tab. =C-c= in the
terminal is what stops the daemon, and it releases the port with it. Re-open the
window by pointing anything at =http://127.0.0.1:PORT/=, or by running =desktop=
again against the same directory on a free port.

*It opens before the tree is indexed.* The window is opened at the socket, not
at the loaded store — see below.

** Serving before the walk finishes

The daemon binds and answers immediately, and walks the tree behind that: over
~6.3k files that is ~16 s during which a browser would otherwise have got a
refused connection. While the walk runs, =/headlines=, =/headline=, =/command=
and =/ws= answer =503= with =Retry-After: 1= and
={"loading": true, "elapsed": 3.4}=,
and =/= plus the assets are served as usual — so the shell paints, shows
=indexing … 3.4s= against an amber dot, and polls once a second until the store
is there. Then it mounts exactly as a warm start does.

#+begin_src sh
curl -sD - -o /dev/null localhost:7777/headlines   # HTTP/1.1 503, Retry-After: 1
#+end_src

The order is fixed: bind, window, walk, watch. The file watch starts after the
walk lands, so its first event cannot fold into a store that is about to be
replaced wholesale.

** Core Architecture

*** ~Data.Org~ — Parser & Data Model

The heart of the project. Key design patterns:

- *Type class-based parsing* via a ~Parse~ typeclass — extensible grammar
- *Stateful parser monad*: ~StateT Context (Parsec Text)~ to track active TODO keywords, categories, and an /Indexed Article Store/ (IAS) across parses
- *A closed sum* (~Element~) over the four node kinds — headline, pragma, timestamp, token — so ~stripSpans~ and the ~TextShow~/~Display~ instances can be total over it

Key types:

#+begin_src haskell
-- Stateful parse with context threading; every element carries its source span,
-- and a failure returns no elements and the caller's context untouched.
orgParse :: Context -> Text
         -> ([Spanned Element], Context, Maybe (ParseErrorBundle Text Void))

-- The REPL monad stack
type Repl a = StateT Org.Context (InputT IO) a
#+end_src

*** ~Repl.Org~ — Interactive REPL

A Haskeline-powered REPL that:
- Accepts raw org-mode text interactively
- Accumulates parser context across inputs
- Shows ~Show~, ~TextShow~, and /display/ representations simultaneously
- Exits on ~:q~, ~exit~, or ~quit~

*** ~Main.hs~ — CLI

- *No argument* → starts the REPL
- *File argument* → parses the file, displays resulting ~Context~, then drops into the REPL
- ~scan DIR…~ → corpus walk with the span-invariant report
- ~serve --dir DIR~ → the web view; see Quickstart
- History stored in =~/.config/glance/.history=
