* Glance — Repository Overview

** Summary

*Glance* is an experimental /stateful org-mode parser/ written in *Haskell*. Its goal is to explore org-mode parsing combined with database interactions, providing a system for managing, querying, and relating org-mode content.

- *Author:* Dmitry Akatov
- *Version:* =0.1.0.0=

** Quickstart — headlines in a browser tab

#+begin_src sh
cabal run glance -- serve --dir ~/org
#+end_src

Then open =http://127.0.0.1:7777/=. The page fetches =/headlines= and mounts
=table-view.js= on it: one row per *top entry* — a level-one headline — with the
state badge, priority, title, tags and the scheduled/deadline dates. Click a
column header to sort, press =/= to summon the filter palette and narrow.

The table is a list of entries rather than of outline lines: a headline written
=**= or deeper has no row, and is reached by materializing the entry it belongs
to (=RET=), which hands over that entry's whole subtree, children included. A
word only a child carries therefore matches no row, and an =ORG_GLANCE_ID= on a
deeper headline addresses nothing. An entry with nothing in any of those columns
— no state, no priority, no title, no tags, no dates — has no row either: the
file keeps it and the table skips it, since a line of six empty cells is nothing
to read. =glance scan= still counts every headline at every level — it is a
parser oracle rather than a view of one.

Nothing has to be installed beside the binary. =table-view.js= is vendored at
=assets/table-view.js= and compiled into =glance=, so a built binary carries the
renderer wherever it is copied and reads no path off this repo.

- =--port N= — default =7777=.
- =--assets PATH= — serve assets out of PATH instead of the compiled-in
  renderer. A development flag: point it at a =table-view= checkout's =web/= and
  reload rather than rebuild (see [[*Hacking the renderer][Hacking the renderer]]).
  It /replaces/ the built-in one, so a PATH without =table-view.js= in it means
  no table — =/= says so and =/headlines= keeps working; the JSON stands on its
  own:

#+begin_src sh
curl -s localhost:7777/headlines | jq '.rows | length'
#+end_src

The response body is the table-view View object and nothing else — the load
counts ride in =X-Glance-*= headers (rows, files, parse, decode and read
failures).

*Filter and page it, and pay for bytes only when something moved.* =/headlines=
takes four parameters and answers with the same View object:

#+begin_src sh
curl -s 'localhost:7777/headlines?q=meeting' | jq '.rows | length'
curl -sD - -o /dev/null 'localhost:7777/headlines?limit=1000&offset=2000'
#+end_src

- =q= — a case-insensitive substring of the row /as it displays/: a bracket link
  matches by its description, and a query never spans two cells. The store keeps
  that text per row, so filtering 13k rows costs one substring scan rather than
  3 MB of JSON on the wire.
- =limit= — page size, at most 20000. Absent means the whole set, which is what
  a client that wants to sort and move locally should ask for.
- =offset= — where the page starts, default 0.
- =order= — =scheduled= (the default) or =document=; see /Walk order/ below.
  Anything else is a 400, since a misspelling that quietly served the sorted
  view would look exactly like a working request.

The filter runs before the page, so =X-Glance-Total= is the match count and
=X-Glance-Has-Next= says whether another page follows. A page is cut out of the
view's own declared sort (scheduled ascending), so page two is the rows the
table would show after page one; sorting a /page/ in the browser reorders that
page alone, while the no-limit mode keeps full-fidelity client-side sort.

*Walk order (experimental).* =?order=document= leaves the rows in walk order
whatever the limit — file by file, top entry by top entry down each — and the
view carries *no =sort= field at all*, so a renderer leaves them where they
landed.

#+begin_src sh
curl -s 'localhost:7777/headlines?order=document' | jq '.rows[:4] | map(.id)'
curl -s 'localhost:7777/headlines?order=document' | jq 'has("sort")'   # false
#+end_src

There is no UI for it: the shell never asks, so this is a URL you type.

Every answer carries =ETag: "<fingerprint>-gN"= — the fingerprint being a
digest of the tree the daemon loaded, =N= the store's generation, which the file
watch moves whenever a response would change — under =Cache-Control:
no-cache=, so a browser revalidates every time and an unchanged tree costs a
0.6 ms 304 instead of a 3 MB body. One tag serves every variant: the parameters
are in the URL and an HTTP cache is keyed by URL, so =?q=foo= and =?q=bar= are
separate entries revalidating against their own tags. Responses are gzipped
(3.06 MB → 580 KB for the whole set, 34 KB → 15 KB for the renderer) with the
=Vary: Accept-Encoding= that goes with it.

*Filtering is a query language.* The filter is summoned rather than resident:
=/= raises a palette over the table, the way a minibuffer opens, and an
unfiltered table carries no filter chrome at all. It speaks
[[file:../table-view/SCHEMA.md][SCHEMA.md]]'s micro-syntax and the server parses
it: =state:TODO state:DONE tanik= is either state and the text, because
distinct keys and free text AND. A =key:value=
is a predicate only when =key= names a column — =state=, =priority=, =title=,
=tag=, =scheduled=, =deadline= — or one of your own org tags, so =:work:= and
==code== stay the org text they are. Tags are keys of their own:
=contact:tanik= is "tagged =contact= and matching =tanik=", and =contact:= alone
is the facet. Two predicates on one key combine by what the field holds: one
value means either of them (=state:TODO state:DONE=, since no row is both),
a list means all of them (=tag:web tag:glance= carries both, the way a label
filter reads). =-token= negates, ="two words"= quotes, =key:none= asks for an
empty cell, =scheduled:2026-08= is the month, =planned:= asks about both date
columns at once (=planned:none= is neither, =planned:2026-08= is either falling
in that month), and =state:*active*= /
=state:*inactive*= are the keyword groups your =#+TODO:= lines declare (=active=
and =inactive= without the stars mean the same thing). A query
with no predicate in it is the substring search it always was. The applied query
rides in the URL, so a filtered view is a link; =DEL= over the table takes the
last token back off.

*The default view is your active work.* Open the page with nothing in the
address bar and it applies =state:*active*= for you — every keyword your
=#+TODO:= lines declare before the bar, which is the work still to do. It is a
query like any you typed: it shows as a chip, it is in the URL, and =DEL= over
the table strips it, at which point the whole tree is on screen. Ask for
something else — =?q=tag:travel=, or an empty =?q== for everything — and that is
what you get; the default is only ever injected when the URL says nothing.

*The page stays tiny.* The shell is inline vanilla JavaScript — no framework, no
build step, no dependency, nothing fetched off this server. It boots on
=?limit=100= — a window's worth, painted well ahead of the whole set's ~250 ms —
pulls the rest in behind the painted table so movement and sorting see
everything, hands the filter to the server rather than narrowing locally,
and opens its socket with =?bootstrap=off= because it already has the rows.

*The tab stays live.* The directory is walked and parsed once, at startup, into
an in-memory store; a request then costs an encode rather than a walk (0.09 s
for 13344 rows against 14.5 s per request before). A file watcher re-parses one
=.org= file per edit — 4 ms — and pushes the difference over =ws://.../ws= as
table-view's streaming ops: =set-rows= once on connect (=?bootstrap=off= drops
it for a client that fetched the rows over HTTP), then =upsert-row= and
=delete-row= per change. Edit a headline in Emacs and the open tab moves in
about 100 ms, no reload; create or delete a file and its rows appear or go. A
green dot in the top-right corner says the socket is up, grey that it is
reconnecting.

*Materialize a headline.* The view declares one action — =RET → materialize= —
so hitting =RET= on the selected row (or double-clicking it) opens that
headline over the table as *two panes and a strip*: a textarea holding the
subtree's text — stars, body and every child, exactly as the file spells them —
a *panel* beside it holding the headline's planning entries and its own property
drawer, and the *logbook* along the bottom.

The panel is one list of rows. The first three are fixed — =SCHEDULED=,
=DEADLINE=, =CLOSED=, in org's order, empty where the headline has no entry —
and hold the timestamp text verbatim; clearing all three is how the planning
line comes off. Under them sit the drawer's properties, in the order the file
writes them. =ORG_GLANCE_ID= is in neither pane: it is the row id the table keys
its updates off, so the server keeps it and puts it back itself. The logbook
strip is read-only, out of Tab and out of every write — it shows the drawer's
lines and the server re-splices the drawer whole.

*The panel is modal*, dired's shape rather than a form's. In *nav* the rows are
read-only text with a cursor on one of them and nothing focusable at all, which
is what leaves the plain letters free: =n= / =p= and =j= / =k= both move the
cursor, and so do the arrows. =RET= opens the row at point, and only then are
there fields to type into: the value takes the focus, and the key takes it where
there is not one yet. A planning row opens its value alone — org owns that key.
Inside an open row =TAB= hops between its two fields, =RET= commits it and goes
back to nav, and =ESC= puts back the text the row was opened on. =+= adds an
empty property at the end and opens it, which is the whole of the "add"
affordance: a key, since there is nothing to press. Empty a key and that
property is deleted on the next sync.

=TAB= crosses between the panes — out of the text into the panel's cursor, out
of nav back into the text — and the cursor is where you left it. There are two
stops, so =S-TAB= is that same toggle rather than a second walk. The crossing is
suspended while a row is open, since inside one row =TAB= has the two fields to
mean. The raw shape =C-c '= swaps to has one pane and nothing to cross to, so
=TAB= is the browser's again there.

The sheet has no buttons. =ESC= is a ladder: over an open property row it is
that row's and puts it back, so the sheet only ever sees the key from nav.
=ESC= from there, or a click outside the box, closes it —
flushing first when *either* pane has moved, and closing on the server's 200; a
sheet you only read closes with no request at all and touches no file. The write
goes back over the same character span, leaving every other byte alone, and the
row arrives a moment later over the socket, because the file watch is what
updates the table whoever did the writing. =C-x C-s= syncs mid-edit and chains
the receipt's digest, so a long session of edits costs no re-materialize. If the
file moved in between — Emacs saved it, a sync landed — the flush is refused and
the sheet stays open saying =conflict=: =C-x C-s= then re-reads the file's digest
and writes your text over it, and =ESC= discards. Closing the tab on an edited
sheet flushes on the way out. The header says which of =synced= / =syncing…= /
=conflict= / =error= it is in — the last two name the key that clears them — and
the sheet wears Hack over the page's own danneskjold.

=C-c '= — org's own =org-edit-special= — swaps the sheet between the two panes
and the raw subtree with the drawer spelled out in the text. It works by asking
the server for the headline again rather than by rearranging anything in the
browser, so an edited sheet is refused with =sync first — C-x C-s=. That is
deliberate: the split between body and drawer is the *server's*, and there is no
org parser in the page to do it locally.

A property nobody edited is written back as the very line it came in on —
spacing, indentation and all — and so is a planning entry nobody changed. Only a
value you changed is re-rendered, as =:KEY: value= under whatever indentation the
drawer already uses, or as =KEYWORD: <stamp>= on the planning line. Decompose and
recompose an untouched headline and the file is byte-identical, permuted planning
lines included. The same round trip from a shell, =id= being the row id the view
carries:

#+begin_src sh
curl -s -G --data-urlencode 'id=ROW-ID' localhost:7777/headline
# → {"org": …, "body": …, "properties": [["EFFORT", "0:30"], …],
#    "planning": [["SCHEDULED", "<2026-08-01 Sat>"], …], "logbook": …,
#    "digest": …, "span": …}

# The whole subtree, as before:
curl -s -X POST -H 'content-type: application/json' \
     -G --data-urlencode 'id=ROW-ID' localhost:7777/headline \
     --data-binary '{"org": "* DONE …\n", "digest": "<the digest the GET returned>"}'

# Or the parts apart, which is what the sheet sends:
curl -s -X POST -H 'content-type: application/json' \
     -G --data-urlencode 'id=ROW-ID' localhost:7777/headline \
     --data-binary '{"body": "* DONE …\n", "properties": [["EFFORT", "0:45"]],
                     "planning": [["CLOSED", "[2026-08-01 Sat]"]],
                     "digest": "<the digest the GET returned>"}'
#+end_src

Both shapes take the same optimistic lock and the same 409s; naming both in one
body is a 400, and an empty =properties= list removes the drawer. Two things are
the *server's* and are in neither shape: =ORG_GLANCE_ID=, which is the row id, and
the =:LOGBOOK:= drawer. They are lifted out of what you are shown and put back
verbatim whatever you send, so a sync that never mentions them cannot move them.
A planning value that no timestamp parser would read back is a 409 naming the
field, with nothing written.

*Settings: the keyword cycles and the default view, from the page.* =,= opens a
second sheet over the table, one section per keyword layer: =system.org= for the
whole tree, then a section per =tags/TAG.org=, then a read-only preview of the
union they add up to. The system section carries one field more — the *default
view*, the query =g= applies and the query a bare page opens on — and one more
after it, the *capture target*, the file =+= writes into. They are the
=#+GLANCE_DEFAULT_FILTER:= and =#+GLANCE_CAPTURE_TARGET:= lines of that same
file, so both ride in that section's own write: one file, one digest, one
splice. Empty the first and the tree goes back to the built-in
=state:*active*=; empty the second and it goes back to =inbox.org= at the root.
Each editable section is one box holding that file's =#+TODO:= lines
*verbatim* — the config files are org and that line is the contract, so what you
edit is the line rather than a chip UI over a guess at what it means. A tree
that has never had a =system.org= still lists it, marked =not created yet=: type
a cycle into it and the file, and the directories over it, are created on the
way out.

It is the materialize sheet's own pattern, down to the words. No buttons: =ESC=
or a click outside syncs the sections that moved and closes, a sheet you only
read closes with no request, =C-x C-s= syncs mid-edit, and the header carries
=synced= / =syncing…= / =conflict= / =error=. Each section is its own file, its
own write and its own lock, so one that Emacs moved underneath you refuses on its
own line while the rest land. What comes back is the *whole tree reparsed*: a
keyword that has just started existing is recognized in files nobody touched, so
the daemon reseeds, the badge palette moves, and every open tab re-fetches. On a
touch device, where there is no chord to type, a gear appears in the status
corner — the same exception the filter's chip row is.

#+begin_src sh
curl -s localhost:7777/config
# → {"layers": [{"path": …, "tag": null, "lines": ["#+TODO: TODO | DONE"], "digest": …},
#               {"path": …, "tag": "book", "lines": […], "digest": …}],
#    "keywords": {"active": […], "inactive": […]}}

curl -s -X POST -H 'content-type: application/json' localhost:7777/config \
     -d '{"path": "…/.org-glance/config/system.org",
          "lines": ["#+TODO: TODO STARTED | DONE CANCELLED"],
          "digest": "<the digest the GET returned>"}'
#+end_src

The write is the same span splice every other write is: only the =#+TODO:=
lines are replaced, so a =#+TITLE:=, a comment and the capture template
org-glance keeps in those files come back byte for byte. A file with no such
line takes one under the header it opens with. Posting an empty =lines= deletes
the layer's cycle. An empty =digest= is the pin for a file that is not there
yet — and a file that turned up meanwhile refuses exactly as a moved one does,
rather than being overwritten. Lines that are not =#+TODO:= pragmas, and pragmas
that declare no keyword org would read, are 400s with nothing written.

The store stays a projection and the org files stay the source of truth: it is
thrown away with the process, every row in it came out of a file, and a file
that stops parsing keeps the rows it had — including one saved from the browser
with a typo in it, which is the same deal any editor offers. Restart the daemon
and the tab re-fetches and re-mounts on its own, backing off from 1 s to 30 s.

*Six keys write without opening anything.* =D= archives, =t= sets a state,
=C-c C-s= and =C-c C-d= set a schedule and a deadline, and =+= captures. The
four that edit rows run over the *marked set* when there is one and over the row
at point when there is not — dired's rule, and org-glance's; =+= names no row at
all, because it makes one. Mark a run of rows with =m=, press =D=, and the pill
says =D → archived (5)=. There is no
confirmation: the page sends row ids and a name, the server works out which
characters to move, and the rows come back over the socket a moment later
because the file watch is still the only thing that updates the table. What
makes that safe is the same optimistic lock the sheet uses — a file that moved
under you refuses its rows and says so in the log, while the rest land.

=t= raises a small palette of the states those rows may be set to, plus
=*clear*= to take a keyword off. It is a *which-key* menu: every entry wears a
letter, that letter commits on its own, and the palette itself is the
confirmation — you have just read the line saying =t= sets =TODO= when you press
=t=. No =RET= behind it and no confirm step; the optimistic lock is what makes a
mis-press cheap.

*The palette is the resolver's answer.* It is a table — =Source= | =Active= |
=Inactive= — with one row per layer that has something to say about the rows you
marked, in the order the resolver consults them: the file's own =#+TODO:= line,
then each of its tags' configs, then =system.org=, then org's built-in
=TODO=/=DONE=. A keyword shows
up under the *nearest* layer that declares it and nowhere below it, so the table
is the classification rule made visible: if =READING= sits in the =book= row,
=book.org= is what makes it active here, and a file that redeclares it takes it
into the =file= row instead. Mark rows across two tags and both tags are rows of
their own.

The chain ends there, and what is *not* in it is the recognition union. A
keyword any layer declares parses as a state in every file under the root — that
is what keeps =STARTED= out of a title — but a =film= keyword is not something a
=book= row, or an untagged one, is configured to be. So it is not on offer and
not settable there, and a state no layer of a row's claims is shown as a state
with nobody's opinion attached: unfinished, and in the default view.

The letters are deterministic. Each entry claims the first letter of *its own
spelling* that no entry above it took, reading the table left to right and top
to bottom, out of one =a=–=z= pool — so =TODO= is =t=, =DONE= is =d=, and
=DELEGATED=, finding =d= gone, is =e=. The claimed letter is *bold where it sits
in the word*, which is the whole of the explanation. Hairlines fall between the
source rows, =*clear*= spans a row at the foot, and it takes its letter out of
the same pool as everything else — =c= where nothing claimed one, =l= where
something did. One tree's keyword cycle always yields the same letters, so the
muscle memory holds.

An entry with no letter left shows a muted =·=. Press =/= for the
completing-read: the table flattens, the letters go, a field appears, type to
narrow, =C-n= / =C-p= or the arrows to walk, =RET= to commit. =ESC= leaves the
palette from either mode.

A keyword is legal per *row*, and the palette and the refusal come from the same
place: what the table shows for a row is exactly what that row may be set to. A
command naming a keyword some row's chain does not declare is refused whole,
naming the keyword and the row, rather than applied to the rows that do declare
it. Mark rows across two tags and the table shows both cycles — commit one of
them and the rows under the other tag are what refuses. The resolution is its
own endpoint if you want it directly:

#+begin_src sh
curl -s 'localhost:7777/keywords?ids=ROW-ID,OTHER-ID'
# {"sources":[{"source":"book","active":["READING"],"inactive":["READ"]},
#             {"source":"builtin","active":["TODO"],"inactive":["DONE"]}],
#  "unknown":[]}
#+end_src

The same commands from a shell:

#+begin_src sh
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "set-state", "ids": ["ROW-ID", "OTHER-ID"], "args": {"keyword": "DONE"}}'
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "archive", "id": "ROW-ID"}'
#+end_src

Rows are grouped by the file they live in and each file is written *once*, so a
marked set spanning three files is three atomic writes rather than one per row.
The answer is per id — =[{"id": …, "ok": true, "digest": …}]=, or an =error=
where a file had moved — in the order you named them. =set-planning= below
answers the same way; =capture=, which names no rows, has its own shape.

*=C-c C-s= and =C-c C-d= reschedule.* Both raise a one-line prompt — the value
palette's overlay with a field in place of its list — titled with the keyword
and how many rows it will run over. Type a date, =RET=, done; type nothing and
=RET= takes the entry off, and when it was the last one on the line the line
goes with it. The two chords are the org spellings, and unlike =C-c C-t= they
*reach the page*: =Ctrl+S= and =Ctrl+D= are page default actions the browser
lets a page claim, where =Ctrl+T= is the browser's own.

The server parses the date, once for the whole request, so a marked set cannot
straddle midnight:

| you type                | it writes                  |
|-------------------------+----------------------------|
| =2026-08-05=            | =<2026-08-05 Wed>=         |
| =2026-08-05 09:30=      | =<2026-08-05 Wed 09:30>=   |
| =today= / =tomorrow=    | today's date / the next    |
| =+3d= / =+2w= / =+1m=   | that far out from today    |
| =<2026-08-05 Wed +1w>=  | exactly that, kept verbatim |

The weekday is *computed* rather than typed — the one thing a reader cannot be
asked to get right — except in org's own bracketed form, where the value is
yours and the only bar is that it reparses. Anything else is a 400 naming what
you typed, and no row moves: half a reschedule over a marked set is worse than
none of one.

#+begin_src sh
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "set-planning", "ids": ["ROW-ID"],
          "args": {"keyword": "SCHEDULED", "date": "+3d"}}'
#+end_src

*=+= captures.* One line of raw org into the tree's inbox: type
=TODO Buy milk :errands:= and that is a keyword, a title and a tag, exactly as
org reads them. The entry is appended at the end of the target with a drawer
holding =:ORG_GLANCE_CREATION_TIME: [2026-08-02 Sun 01:30]= — org-glance's own
property, in org's inactive form, on the server's clock — and the row arrives in
the table a moment later over the same file watch every other write goes
through. The creation time is the server's, so the sheet never offers it for
editing and a sync that never mentioned it puts it back untouched, exactly as it
does the row id.

Where it lands is =#+GLANCE_CAPTURE_TARGET:= in =system.org=, resolved against
the served root; with no line anywhere it is =<root>/inbox.org=, and a target
that is not there yet is *created*, directories and all, under the same lock
every other write uses. A target outside the tree — an absolute path, one
climbing out through =..=, or a name the walk would not read — is refused when
the config is read rather than when you press =+=: the startup banner says where
captures will go, and a misconfigured tree says so there.

#+begin_src sh
curl -s -X POST -H 'content-type: application/json' localhost:7777/command \
     -d '{"name": "capture", "args": {"text": "TODO Buy milk :errands:"}}'
# → {"ok": true, "file": "…/inbox.org", "digest": …}
#+end_src

*=D= archives; it never deletes.* The tag org uses goes on the headline
(=:web:glance:= becomes =:web:glance:ARCHIVE:=, and a headline with no tags gets
=:ARCHIVE:= appended to its title line) and everything else about the file stays
where it was. Pressing =D= twice costs nothing: a row already carrying the tag
is left alone. What makes an archive worth having is the other half — the table
leaves archived rows out unless you ask for them:

| query              | what you get                                 |
|--------------------+----------------------------------------------|
| (nothing)          | everything except archived rows              |
| =archive:=         | the archived rows                            |
| =-archive:=        | everything except them — the default, spelled |
| =archive:tanik=    | archived rows matching =tanik=                |

Any query that mentions the =archive= key at all turns the default off, and the
response's =X-Glance-Archived= header says how many rows were left out, so an
empty table can be told from one whose matches are all filed away. The key stays
in the vocabulary whether or not the default is hiding its rows, which is what
makes it reachable at all: the filter is parsed against every tag in the tree,
and only the rows are narrowed.

*=o= follows the row.* An org entry that points somewhere — a bracket link on
the title, a bare URL in the body, a reference under a child — is a row you can
leave from. =o= (or =!=, org-glance's other spelling) asks the server what this
row points at and then does the obvious thing: nothing to follow is a refusal
that says so, *one* link opens in a new tab, and *several* raise the same
palette =t= uses, one letter each, over the descriptions the entry itself
wrote. =/= there narrows over the descriptions *and* the targets, since you may
remember the host and not the wording. Every open writes a line into the log
naming what was followed.

Finding the links is the server's job, not the page's. The rule is the one the
table already reads a cell with — =[[TARGET][DESC]]= shows =DESC=, =[[TARGET]]=
shows the target — plus bare =http=, =https= and =mailto:= URLs, which describe
themselves and stop before the punctuation a sentence leaves behind. Order of
appearance, one entry per target. The browser holds no org parser and this is
why it does not need one.

#+begin_src sh
curl -s 'localhost:7777/links?id=ship-table-view'
# → {"links": [{"target": "https://…", "desc": "the table view"}]}
#+end_src

*=a= is the agenda, and it is a view rather than a mode.* It applies
=state:*active* -planned:none= — your live work, narrowed to the entries
carrying a date — and sorts it by schedule, earliest first. There is nothing to
leave: the query is in the URL and in the filter chips like any other, =DEL=
strips a token off it, and =g= puts the default view back. =planned= is a filter
key of its own, so the halves are yours to recombine: =planned:none= is
everything nobody has put a day on, =planned:2026-08= is a month's worth of
schedules and deadlines together, and =-planned:none deadline:2026-08= narrows
to the ones with a due date in it.

*Keys.* The page carries org-glance's =overview-mode= map, under org-glance's
own command names, and echoes what it did in a pill in the bottom corner — the
pending prefix while one is open (=C-c -=), the command and its help line on
completion (=C-c C-t → org-glance-overview:todo=), =C-c z is undefined=
otherwise, and the prefix drops after two seconds.

There is *one map*. The =emacs= and =vim= movement profiles are gone, and what
replaced them is both spellings bound at once: a table has no text field to
compete with, so =n= and =j= can both step a row and cost a table row each —
where a profile cost a selector in the corner, a remembered choice, a =?keys==
parameter and a key line that had to be rewritten whenever it moved.

*One of those does not survive the browser.* =C-c C-t= is bound, dispatched and
claimed by the page — and in Chromium the second chord never arrives, because
=Ctrl+T= opens a tab in the browser process above the document and
=preventDefault()= cannot reach it. Firefox reserves it the same way. The page's
half is correct and tested; there is nothing a page can do about the other half,
which is why the same command answers to a plain =t=. The chord stays bound for
browsers that deliver it — and for the native window (=-f native-window=), which
has no chrome to bind =Ctrl+T= to and delivers it like any other key.

The other three chords are fine. =C-x C-s=, =C-c C-s= and =C-c C-d= end on keys
the browser treats as *page default actions* — save, save, bookmark — which a
page is allowed to claim, so =preventDefault()= reaches them and the sequence
completes. It is =Ctrl+T=, =Ctrl+N= and =Ctrl+W= that never arrive.

No sequence is bound twice, and none opens a longer one — which is why =gg= and
=dd= are not in the map: a complete sequence that also opens a longer one leaves
the longer one unreachable.

Horizontal movement selects a *cell*. =f= and =b= are org-glance's same-level
keys one granularity down — where the overview walks headlines with them, a
table walks the cells of a row — and =l= and =h= are the same two commands under
vi's spelling. A row selection starts with no column and looks exactly as it always did;
the first horizontal key lands on the first column whichever direction asked
for it, and from there =n=/=p= (=j=/=k=) carry that column down the table.
Walking off either edge stays on it. The echo names where it landed by the
column's own header — =f → next-column (Headline)=, or =f → next-column (at
last)= at the edge. The column lives in the renderer's selection rather than in
the page, so it rides along with row movement and clearing the selection takes
it with it.

Rows *mark* the way dired's do. =m= toggles the mark on the row under the cursor
and steps to the next, so a held =m= walks a column laying marks down; =u= only
ever takes one off, and steps too, so a held =u= clears a column rather than
flickering it; =U= drops the lot and =M= marks every row loaded, the page it is
not showing included. Each echoes the count the renderer keeps
(=m → marked (3)=, =U → all marks and flags cleared=), and the renderer's own status line
leads with =3 marked ·= while any stand. The marks themselves are the
renderer's, keyed by row id: a marked row that a filter hides, that a page turn
leaves behind or that a sort moves is still marked, and still counted, because
the count is what a bulk action would run over. Nothing on this page keeps a
second copy of them.

The set is shown a *page* at a time — 100 rows, the same count the first paint
asks the server for, so the opening screen is exactly page one and everything
arriving behind it only adds pages to turn to. The pager reads in the renderer's
own status line (=1–100 of 12,870 · ‹ prev · next ›=) and is absent while there
is one page. =]= and =[= turn one and echo where they landed — =] → page 3/129=.
Row movement crosses the boundary by itself: =n= off the last row of a page
lands on the first row of the next, =p= off the first lands on the previous
page's last, and the column rides along either way. Where the page ends is the
renderer's to know, since only it knows there is one. The buffer-ends keys reach
the ends of the page on show — =<= and =>=, with =G= beside =>= — so =[= and =]=
are how you leave it.

*Archiving is two presses.* =d= flags the row under the cursor and says so
(=d → flagged — d again archives=); a second =d= on that same row archives it.
=D= is the same idea over the whole flagged set — flag a few rows, then =D= —
and falls back to the row at point when nothing is flagged. The pill names the
set it ran over: =D → archived (4 flagged)=, or =D → archived (row)=. The flag
is the confirmation, so there is no prompt and no undo to build; =u= takes a flag
off before it touches a mark, and =U= clears both. Flags are keyed by row id like
marks, so one survives a filter, a page turn and a re-sort, and nothing has to
clear them after a =D= — the rows carry the tag now and leave the default view.
Both keys are held-key-safe: a key you lean on delivers exactly one press.

*Marks and flags are different selections, on purpose.* A mark is the generic
bulk selection — lay a run of them down and =t= sets a state over the lot. A flag
is a selection made for archiving and nothing else. =D= reads flags and never
marks, which is what stops a mark you laid down for a state change from becoming
a row you archive by reflex.

Switch in the status corner, top right: the connection dot and a =theme:=
selector, in that order. It is a native =select=, so Tab reaches it and the
arrows walk it without a chord of its own.

*Light or dark, and no flash either way.* =theme:= offers =auto=, =light= and
=dark=. =auto= follows the system's =prefers-color-scheme= and is the default;
the other two stamp =data-theme= on the document element and pin it, and
choosing =auto= again takes the attribute back off. The choice is remembered in
=localStorage= under =glance-theme=, and a one-line script in the =<head>= reads
it and stamps the attribute before the first paint, so a dark-themed page never
flashes light on the way in. The whole page wears danneskjold through one set of
=--g-*= variables — surface, text, muted text, border, selection — and the
materialize sheet keeps a single =--dk-mono= of its own, the Hack font stack.

The page's last line is that map, resident: =n/p rows · f/b cells · [/] pages ·
RET materialize · m/u/U/M mark · t state · d flag for archive · d/D archive
flagged · / filter · g default view · DEL drop token · , settings · q quit=. It is named by
command and spelled from the same blob the dispatch reads, so it can never offer
a key nothing is bound to. The pill says what just ran; the line says what can.

The page itself never scrolls. It is one column the height of the window — the
table, the log under it taking whatever is left, the key line last — and the two
boxes that can outgrow their room scroll inside themselves, so the corner and
the key line hold their places whatever arrives.

*The log under the table is an event log, and it keeps everything.* A line reads
=14:03:22 info cmd headline "Ship the thing" archived=: a clock, a severity
(=info=, =warn= or =error=, the word coloured so a warning is findable in a
screenful), a scope saying which part of the page is talking (=ws=, =sync=,
=cmd=, =filter=, =config=, =boot=), and the message. Nothing ever clears it —
the boot line is an ordinary line and stays at the bottom of the scrollback —
so what went past while you were reading the table is still there to scroll back
to. It holds the last five hundred entries and drops the oldest past that, and a
message repeated straight after itself is counted on its own line (=×7=) rather
than written out again, which is what keeps a retry loop from crowding
everything else out. The end is kept in view unless you have scrolled up, in
which case the place you are holding is left alone. Writes name their rows there
— =headline "TITLE" marked for deletion= when =d= flags one, =archived= when it
lands, =→ DONE= when a state does — one line per row, so a bulk command that
came back two-thirds applied says which third.

A staged key is recognized in full and then says what it is waiting for: the map
is complete ahead of the commands that will back it, which reads better than a
key that silently does nothing. The keys are inert while a text field has focus
— typing in the palette or the sheet types — and while the property panel is
holding them, which it does with nothing focused at all; the exceptions are
=C-x C-s=, =C-c '= and =ESC=, which is what makes the sheet's Emacs muscle
memory work, over the properties panel as much as in its textarea. =C-c= and =C-x= become
prefixes only with the selection collapsed, so a copy or a cut is still one, and
=C-l=, =C-r=, =C-t=, =C-w=, =C-n=, =C-p= and =<f5>= always reach the browser —
which is why nothing moves on =C-n= or =C-p=, however much Emacs would like to.
The native window (=-f native-window=) is a bare web view with no chrome to
reserve them, so there they reach the page like every other key.

*On a touch device there are no keys*, which is the one exception the
keyboard-first rule makes. A coarse pointer gets the chip row as a tap target —
44px of it, reading =filter …= while nothing is applied — and tapping it summons
the palette =/= summons. The sheet's textarea and its property fields are 16px
there, since iOS zooms the page in on anything smaller and does not zoom back
out, and the two panes stack rather than sitting side by side. A mouse or a
trackpad sees none of this: every rule is inside =@media (pointer:coarse)= and
the tap handler asks the same query before it runs. A narrow window stacks them
too, by wrapping rather than by a breakpoint of its own.

The whole page is monospace — /JetBrains Mono/, /Fira Code/, /SF Mono/, Menlo,
Consolas, whichever is installed. Nothing is fetched for it. Drop a
=JetBrainsMono-Regular.woff2= (or =.ttf=) into an =--assets= directory and the
shell declares an =@font-face= against it and serves it from there; leave it out
and the stack falls through, silently. No font is compiled in — the renderer is
the whole of what the binary carries — so a run without =--assets= uses whatever
the machine has.

*What is not walked.* org-glance keeps its canonical store under
=.org-glance/data/= and writes overview and agenda buffers beside it under
=.org-glance/overviews/= and =.org-glance/meta/=, repeating the same headlines
under the same =ORG_GLANCE_ID=. Those two directories are skipped — org files
are the source of truth, and a derived render of one is not a second headline.
Over =~/sync= that is 514 fewer rows and one duplicated row gone from a filtered
table. =--include-derived= walks them anyway, on =serve=, =desktop= and =scan=.
Where two files still claim one id, the =.org-glance/data/= copy wins and the
rest are counted in =X-Glance-Id-Collisions= and listed by =glance scan=.

The listener binds =127.0.0.1= and nothing else. Authentication and the
read/write/automate tiers arrive with the protocol step (S7 in
=docs/plan-org-console-web.md=); until then the loopback interface is the whole
access-control story.

** Desktop — the same server, in a window of its own

#+begin_src sh
cabal run glance -- desktop --dir ~/org
#+end_src

The same daemon =serve= runs, with a window opened on it the moment the socket
is listening: no address bar, no tabs, no chrome. It takes =serve='s flags —
=--dir=, =--port= (default 7777), =--assets=, =--include-derived= — plus three
of its own:

- =--browser CMD= — what to open the window with.
- =--dry-run= — print the command that would be run and the URL it would open,
  then exit. Nothing is bound and nothing is started, so it is the way to see
  what this machine resolves to:

#+begin_src sh
cabal run -v0 glance -- desktop --dir ~/org --port 7797 --dry-run
# glance desktop — http://127.0.0.1:7797/
#   window:  /usr/bin/chromium --app=http://127.0.0.1:7797/
#   dry run — nothing started.
#+end_src

- =--keep-serving= — leave the daemon running when the window closes. It means
  something only for a window this binary owns; see below.

*Which browser.* =$GLANCE_BROWSER= first, then =--browser=, then the first of
=chromium=, =chromium-browser=, =google-chrome-stable=, =google-chrome=,
=brave=, =vivaldi= found on =PATH= — each run as =CMD --app=http://127.0.0.1:PORT/=.
The environment leads so a machine whose browser is on none of those lists can
be set up once, in a shell profile, and be obeyed by every launcher too. What it
names has to be a chromium-family browser: =--app= is the flag that drops the
chrome, and Firefox no longer has it.

With none of them installed, =xdg-open= opens the URL as a plain tab instead —
a worse window and a working one. With no =xdg-open= either, the URL is printed
and the server keeps serving: a missing browser never takes the daemon with it.

*Closing a borrowed window leaves the daemon running.* It is a browser window,
and the server behind it is a server — closing it is closing a tab. =C-c= in the
terminal is what stops the daemon, and it releases the port with it. Re-open the
window by pointing anything at =http://127.0.0.1:PORT/=, or by running =desktop=
again against the same directory on a free port.

*It opens before the tree is indexed.* The window is opened at the socket, not
at the loaded store — see below.

*** A window of its own: =-f native-window=

#+begin_src sh
make native                           # then: glance desktop --dir ~/org
#+end_src

Built with that flag, =glance desktop= opens a WebKitGTK window itself instead
of borrowing a browser: 1200x800, titled =glance — DIR=, black before the first
paint. Naming a browser still wins — =$GLANCE_BROWSER= and =--browser= beat the
native window in every build — and =--dry-run= says which won:

#+begin_src sh
# glance desktop — http://127.0.0.1:7797/
#   window:  native window (WebKitGTK) — glance — /home/x/org
#   dry run — nothing started.
#+end_src

*The keys are the reason.* Chromium and Firefox take =Ctrl+T=, =Ctrl+N= and
=Ctrl+W= in the browser process, above the document, so =C-c C-t= cannot
complete in a borrowed window whatever the page does about it (see the keymap
section). A bare web view has no chrome to bind them to, so every chord the page
claims reaches it.

*Here the window is the app.* Closing it stops the daemon and releases the port;
=C-c= does the same from the terminal. =--keep-serving= puts the borrowed
window's semantics back, for a session that wants the server to outlive it. A
window that fails to open leaves the daemon serving either way — no window
failure has ever taken this daemon down.

*The flag is off by default, and manual.* On, the solver pulls some 28 packages
(the =gi-gtk3= tree, =gi-webkit2= and what they generate from the system's
typelibs) and the build needs GTK3 and WebKitGTK development files. Off, nothing
above is resolved, the test suite runs without GTK, and =glance desktop= is the
browser launcher exactly as described above. =cabal build all= is the unflagged
build either way: the native packages live in a project file of their own, so
they are built when they are asked for and never otherwise.

*Why =make native= rather than =cabal build -f native-window all=.* Two things
this repository has to supply before the flag can resolve at all.

- Every Hackage =gi-webkit2= binds *WebKit2 4.0* — the =libsoup2= generation —
  and Arch has dropped it; the machine carries =webkit2gtk-4.1= (soup3) alone,
  and there is no =webkitgtk-6.0= for the GTK4 binding either. =vendored/= holds
  =gi-webkit2= and =gi-javascriptcore4= repointed at the 4.1 typelibs: each is
  upstream's tarball with a handful of lines marked =glance:= changed —
  =pkgconfig-depends=, the typelib version in =Setup.hs=, and =gi-soup2= →
  =gi-soup3=. The 4.0 and 4.1 C APIs are the same modulo that swap, which is
  what makes the patch that small. =cabal.project.native= names them and turns
  the flag on, so neither can be had without the other.
- =vendored/gir/= holds =cairo-1.0=, =xlib-2.0= and =freetype2-2.0=, the
  hand-written GIR files every GTK binding reads at configure time. They ship in
  Arch's =gobject-introspection=, which this machine does not have — only
  =gobject-introspection-runtime=, which carries the typelibs and no GIR.
  =make native= points =HASKELL_GI_GIR_SEARCH_PATH= at them, which is the one
  thing a project file cannot say. haskell-gi searches that path first and the
  system's after, so installing the package makes the directory dead weight
  rather than a conflict.

*What compiling proves, and what it leaves.* The flagged build type-checks and
links =Glance.Desktop.WebKit= against the real bindings, unchanged from the way
it was written blind, and warning-free; nothing here has opened its window. Still to be seen by eye: the chords arriving in a chrome-less web
view (the reason this exists), the black first paint, closing the window
stopping the daemon, =C-c= reaching the GTK loop, and a missing display leaving
the daemon serving.

*Maintenance.* Both vendored packages keep upstream's name and version on
purpose — a local package shadows every Hackage version of its name, so those
directories are the only =gi-webkit2= and =gi-javascriptcore4= the solver can
see, and =cabal get NAME-VERSION && diff -r= is the whole patch. An upstream
release that binds WebKit2 4.1 retires =vendored/=; a distribution that ships
=gobject-introspection= retires =vendored/gir/=.

** Serving before the walk finishes

The daemon binds and answers immediately, and walks the tree behind that: over
~6.3k files that is ~16 s during which a browser would otherwise have got a
refused connection. While the walk runs, =/headlines=, =/headline=, =/keywords=,
=/command=, =/config= and =/ws= answer =503= with =Retry-After: 1= and
={"loading": true, "elapsed": 3.4}=,
and =/= plus the assets are served as usual — so the shell paints, shows
=indexing … 3.4s= against an amber dot, and polls once a second until the store
is there. Then it mounts exactly as a warm start does.

#+begin_src sh
curl -sD - -o /dev/null localhost:7777/headlines   # HTTP/1.1 503, Retry-After: 1
#+end_src

The order is fixed: bind, window, walk, watch. The file watch starts after the
walk lands, so its first event cannot fold into a store that is about to be
replaced wholesale.

** Hacking the renderer

The table is drawn by [[https://github.com/rails-to-cosmos/table-view][table-view]], which lives in its own repository and is
vendored here as =assets/table-view.js= — a committed file, read at *compile*
time and carried in the binary. The loop for changing it:

#+begin_src sh
# 1. hack it in the sibling checkout, serving it off disk — no rebuild per edit
cabal run glance -- serve --dir ~/org --assets ../table-view/web

# 2. bring the result back into this repo, and see what moved
make sync-renderer

# 3. commit assets/table-view.js like any other file, and rebuild
git add assets/table-view.js && cabal build
#+end_src

=make sync-renderer= copies =../table-view/web/table-view.js= over the vendored
copy and prints the diff summary; without that sibling checkout it says so and
changes nothing, so a clone of this repository alone still builds and still
serves the page.

That the binary is self-contained is a rule rather than a convenience: no source
file here may name an absolute path outside the repository, and the suite sweeps
=src*/= and =app/= for one (=test/TestSelfContained.hs=). The renderer used
to be read at run time out of one machine's home directory, which meant a
=glance= copied anywhere else served a page with no table on it.

** Core Architecture

*** ~Data.Org~ — Parser & Data Model

The heart of the project. Key design patterns:

- *Type class-based parsing* via a ~Parse~ typeclass — extensible grammar
- *Stateful parser monad*: ~StateT Context (Parsec Text)~ to track active TODO keywords, categories, and an /Indexed Article Store/ (IAS) across parses
- *A closed sum* (~Element~) over the four node kinds — headline, pragma, timestamp, token — so ~stripSpans~ and the ~TextShow~/~Display~ instances can be total over it

Key types:

#+begin_src haskell
-- Stateful parse with context threading; every element carries its source span,
-- and a failure returns no elements and the caller's context untouched.
orgParse :: Context -> Text
         -> ([Spanned Element], Context, Maybe (ParseErrorBundle Text Void))

-- The REPL monad stack
type Repl a = StateT Org.Context (InputT IO) a
#+end_src

*** ~Repl.Org~ — Interactive REPL

A Haskeline-powered REPL that:
- Accepts raw org-mode text interactively
- Accumulates parser context across inputs
- Shows ~Show~, ~TextShow~, and /display/ representations simultaneously
- Exits on ~:q~, ~exit~, or ~quit~

*** ~Main.hs~ — CLI

- *No argument* → starts the REPL
- *File argument* → parses the file, displays resulting ~Context~, then drops into the REPL
- ~scan DIR…~ → corpus walk with the span-invariant report
- ~serve --dir DIR~ → the web view; see Quickstart
- History stored in =~/.config/glance/.history=

** Org-Mode Features Supported

- Multi-level headlines (~*~, ~**~, ~***~ …)
- TODO/DONE states with *dynamic keyword registration* via ~#+TODO:~ pragma
- Priorities (~[#A]~, ~[#B]~, ~[#C]~)
- Tags (~:tag1:tag2:~)
- ~:PROPERTIES: ... :END:~ blocks
- Active ~<YYYY-MM-DD>~ and inactive ~[YYYY-MM-DD]~ timestamps with repeater intervals
- ~#+CATEGORY:~ pragma
